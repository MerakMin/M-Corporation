# 채널 연결 안내

## 패션플러스 고객문의 전용 수집기

`fashionplus-1` 고객문의 게시판은 `fashionplus-qna-readonly` 수집기를 제공합니다. 2026-10-23의 구조 보고서로 확인한 표 항목명과 목록/상세 문의번호를 사용하며 별도의 CSS 선택자가 필요하지 않습니다. [윈도우 연결 순서](WINDOWS.md#4-패션플러스-고객문의-수집-연결)를 따르세요. 기존 사용자가 직접 입력한 매핑은 업그레이드로 덮어쓰지 않습니다.

수집 대상은 `답변대기`·`미확인`이며, 완료 문의는 새 대기 문의로 추가하지 않습니다. 목록 전체 건수와 페이지 수를 대조하고 고객명·브랜드 불일치, 중복 상세 번호·페이지, 불완전한 페이지 이동 시 해당 수집 결과 전체를 저장하지 않습니다. 숫자 페이지 링크가 없는 구간은 성공으로 간주하지 않고 중단합니다. 날짜 필터는 사이트 초기 범위를 유지하고, 프로그램의 문의 시간에는 최초 수집 시각을 사용합니다. 여러 브랜드가 섞여 있으면 브랜드 필터/계정 설정을 확인해야 합니다.

목록 번호와 상세 문의번호는 별도 식별자입니다. 두 번호가 같다고 가정하거나 번호 차이를 계산해 주소를 만들지 않습니다. 해당 목록 행의 제목을 실제 클릭해 열린 새 창(또는 같은 탭)을 읽고, 가림 문자를 제외한 고객명과 브랜드를 확인합니다. 목록 번호는 기존 중복 제거 키로 유지하며 상세 문의번호를 별도 저장합니다. 서로 다른 목록 행이 같은 상세 번호로 연결되거나, 재수집 시 저장된 두 번호의 연결이 달라지면 저장하지 않습니다. 프로그램에서 두 번호를 함께 표시하고 실제 열린 상세 주소를 원문 링크로 사용합니다.

전용 수집기는 읽기와 초안 작성만 지원합니다. **초안 복사 → 원문에서 답변**으로 등록하며, 원문에서 수동 등록한 답변은 다음 수집 때 저장된 상세 URL을 다시 읽어 명시적인 `답변완료` 상태를 확인하면 완료로 반영합니다. API로 전송을 요청해도 차단합니다. 실제 운영 사이트의 로그인 세션은 사용자 PC에 있으므로 재현 화면 테스트와 실사이트 검증을 구분합니다. CS알리미는 아래 별도 운영 알림 수집기를 사용하고, 범용 연동에는 기존 선택자 설정이 필요합니다.

패션플러스 고객문의·CS알리미와 쿠팡 고객 문의 전용 수집기 외의 범용 수집·전송에는 **문의 URL, 해당 PC의 로그인 세션, 화면 선택자 매핑**이 필요합니다. 플랫폼별 완성형 공식 API 커넥터나 검증된 선택자가 포함된 것은 아닙니다.

PDF의 ‘로그인만 해 두면 동작’은 별도의 브라우저 조작 에이전트를 전제로 합니다. 이 구현은 로컬 Playwright 브라우저를 사용하므로 평소 사용하는 Chrome 로그인과 세션이 분리됩니다. PC를 바꾸면 로그인도 다시 해야 합니다.

## 쿠팡 화면 구조 진단

`05-inspect-coupang.cmd`의 1번은 `coupang-1` 고객 문의, 2번은 `coupang-0` 고객센터 문의를 진단합니다. 명령행에서는 `node scripts/inspect-coupang.js product` 또는 `node scripts/inspect-coupang.js center`를 실행합니다. 등록된 문의 주소와 `.data/profiles/coupang` 로그인 프로필을 사용합니다. 실행 전에 서버와 기존 로그인 브라우저를 종료합니다.

진단 도구는 화면 구조만 저장합니다. 제공된 고객 문의 자료로 아래 전용 수집기를 추가했으며 고객센터 문의는 아직 별도 자료가 필요합니다. [윈도우 단계별 안내](WINDOWS.md#6-쿠팡-문의-화면-진단)를 참고하세요.

## 쿠팡 고객 문의 전용 수집기

`coupang-1`은 `coupang-product-readonly` 수집기를 사용합니다. 2026-11-04 사용자가 제공한 구조 보고서와 화면에서 각 문의가 별도 `tbody`이고 6열 목록 행 뒤에 날짜가 있는 답변 행이 이어지는 것을 확인했습니다. **접수번호**를 중복 제거 키로 사용하며 주문번호나 가려진 고객명으로 문의를 식별하지 않습니다. 문의 본문·상품명·고객 표시명·등록 시각을 읽고, 기존 답변은 최신 본문과 등록 시각을 따로 저장합니다. 화면의 한국 시간을 UTC로 변환해 저장합니다. 원문 링크는 문의 목록 주소이며 접수번호로 해당 문의를 직접 찾아야 합니다.

답변여부 검색 조건만 `전체`로 선택하고 날짜·상품 필터는 사이트가 표시하는 값을 유지합니다. `추가답변` 표시와 날짜가 있는 답변 본문을 함께 확인해야 완료로 인정합니다. 미답변은 명시적인 답변 버튼/미답변 표시와 게시 답변 없음이 모두 충족되어야 합니다. 확인하지 못한 행 구조·중복 접수번호·잘못된 날짜·열린 입력창·불일치는 수집 실패로 처리합니다. **전체 건수와 현재 읽은 건수가 같을 때만 저장하며 여러 페이지 이동은 아직 지원하지 않습니다.** 자동 클릭은 답변여부 필터와 검색 버튼으로 제한합니다. 답변·추가답변·등록·비노출 버튼은 누르지 않습니다.

기존 대기 문의도 이번 목록에 나타나고 접수번호·본문·상품명·고객 표시명·등록 시각이 일치하면 완료로 갱신합니다. 목록에서 사라지거나 조회 기간 밖이라는 이유로 완료 처리하지 않습니다. 원문 답변은 `completion_origin=remote_reply`, `sent_body`, `sent_at`에 저장하며 편집 중인 초안을 덮어쓰지 않습니다. 완료 후 추가 답변도 같은 문의의 최신 답변으로 갱신합니다. 동일 답변 재수집은 버전·이벤트를 중복 증가시키지 않습니다. 재개·삭제·비노출 후 상태 복구는 아직 지원하지 않습니다.

기존 기본 URL에 선택자를 매핑하지 않은 설정만 전용 수집기로 이관하며 해당 문의함은 비활성 상태로 둡니다. 사용자 URL·선택자는 유지합니다. API와 브라우저 전송 경로 모두 직접 전송을 차단합니다. **고객센터 문의의 수집 선택은 끄고 고객 문의만 켜세요.** 재현 화면과 UI 테스트는 통과했으며 실사이트 자동 수집은 사용자 PC에서 확인해야 합니다.

## 패션플러스 완료 상태 동기화

사용자가 원문 답변 등록 후 프로그램의 **답변 완료** 탭으로 이동한 것을 확인했습니다.

활성화된 고객문의 수집함에서 이미 저장된 `pending`·`failed` 문의를 확인합니다. 답변대기 목록에서 사라졌다는 사실만으로 완료 처리하지 않으며, 저장된 상세 URL의 상세 문의번호·고객명·브랜드가 일치하고 `문의상태`가 정확히 `답변완료`여야 합니다. `처리완료`, 로그인 화면, 해석할 수 없는 상태는 완료 근거로 사용하지 않습니다. 예시 모드와 비활성 문의함, 이미 완료된 문의는 대상에서 제외합니다.

완료 확인은 새 목록 수집과 분리됩니다. 새 목록 읽기가 실패해도 먼저 검증한 완료 건은 유지하고, 완료 확인에 실패해도 새 문의 수집은 시도합니다. 결과에는 추가 건수와 완료 반영 건수를 각각 표시합니다. 서버가 실행 중일 때 10분마다 또는 **지금 수집**으로 실행하며 자동 답변 등록은 하지 않습니다.

완료 상태는 `sent`, 출처는 `completion_origin=remote_status`, 확인 시각은 `remote_status_checked_at`에 저장합니다. 실제 게시 본문과 등록 시각은 읽지 않았으므로 `sent_body`·`sent_at`은 비워 두고 현재 초안을 그대로 보존합니다. 화면은 이를 **저장된 초안**으로 표시합니다. 완료를 반영하면 버전을 올려 이전 화면에서의 수정·전송 요청을 막으며, 재수집해도 완료 이벤트를 중복 생성하지 않습니다. 이미 완료로 반영한 문의의 재답변 요청·재개 상태 동기화는 이번 범위에 포함하지 않습니다.

### 패션플러스 CS알리미와 고객문의 게시판

등록된 `/cs-center/cs-notification?status=1` 주소는 **CS알리미**입니다. 2026-10-22 사용자가 제공한 화면과 구조 보고서에서 패션플러스의 자동 배송 관리 알림임을 확인했습니다. 고객이 직접 남기는 문의 게시판과 구분해야 합니다. 초기 기본 이름 ‘고객 문의’는 해당 원래 주소에 한해 ‘CS알리미’로 정정하며, 사용자가 변경한 이름·주소·선택자는 보존합니다.

확인된 목록은 문의번호·처리상태·브랜드·주문번호·고객명·문의유형·문의일자·회신기한을 표시합니다. 헤더 표와 데이터 표가 분리되어 있고, 처리상태의 링크에서 상세 화면을 엽니다. 상세에는 ‘문의상태’, ‘문의종료여부’, ‘상품명’, ‘알림내용’ 등이 있으며, 확인한 완료 건에는 답변 입력란이나 등록 버튼이 없습니다. ‘답변완료’라는 상태만으로 판매자가 고객에게 보낸 답변 본문이 존재한다고 판단하지 않습니다. 미처리 건의 입력 화면은 아직 확인하지 않았습니다.

CS알리미 전용 읽기 수집기 `fashionplus-notifications-readonly`를 추가했습니다. 이전 JSON 파일은 현재 다시 다운로드할 수 없었으며, 대화에 남은 화면과 이 문서의 구조 설명을 사용했습니다. 재현 화면 테스트와 사용자 PC의 실제 수집 검증은 구분합니다. 기본 URL에 선택자가 없는 기존 CS알리미만 전용 수집기로 이관하고 수집 선택은 비활성으로 둡니다. 기존 고객문의 설정, 사용자 URL·선택자·로그인 프로필·저장된 문의를 보존합니다.

목록의 문의번호와 실제 처리상태 링크 클릭으로 열린 상세 URL을 저장합니다. 상세 화면에는 별도 문의번호가 확인되지 않아 임의로 만들지 않습니다. 목록과 상세의 주문번호·순번, 고객명/주문자, 브랜드를 대조하고 빈 본문·상품명, 중복 번호·상세 URL, 불완전한 페이지 이동은 저장하지 않습니다. 고객문의와 CS알리미의 번호가 같아도 `(mode, channel, source, external_id)` 키로 분리합니다. 조회 날짜·상태는 사이트 초기 범위를 유지합니다.

CS알리미는 `inquiry_kind=notification`으로 저장하며 고객 답변 초안을 생성하지 않습니다. API의 초안 편집·재작성·전송 및 브라우저 전송 경로를 차단합니다. 알림 본문에 적힌 주문 상태·출고일·취소 처리 안내를 프로그램이 자동 실행하지 않습니다. `remote_status`, `remote_closed`, `response_due`, `order_reference`로 상태·종료 여부·회신기한·주문번호/순번을 보존합니다. 원문 상태가 답변완료/처리완료이면서 종료 여부가 종료인 경우에만 `status=sent`, `completion_origin=remote_notice`로 처리 완료를 표시합니다. 실제 답변을 게시한 것으로 표시하거나 답변 본문·게시 시각을 만들어 저장하지 않습니다.

이미 저장된 대기 알림은 목록 수집 전에 원문 URL을 재확인합니다. 주문번호·주문자·브랜드·상품명·본문이 일치해야 종료 상태를 갱신합니다. 완료 알림도 조회 목록에 나타나면 상태 변경을 반영하지만, 조회 범위 밖의 완료 알림이 다시 열린 경우는 추적하지 않습니다. 상세 확인 후 목록 수집 실패가 나도 확인된 종료 상태는 유지합니다. 새 목록 수집·저장은 문의함별로 독립 처리하므로 한 쪽 실패가 다른 쪽 성공 결과를 취소하지 않습니다. 전체 채널 상태는 오류를 표시해 부분 성공을 숨기지 않습니다.

윈도우에서는 [두 문의함 연결 안내](WINDOWS.md#8-패션플러스-두-문의함-함께-사용하기)를 따르세요. 업데이트 후 사용자 PC에서 실제 수집을 확인해야 합니다.

### 네이버 계정 구분

비욘드와 쿼터의 URL은 동일하지만 브라우저 프로필 경로가 각각 `.data/profiles/smartstore`, `.data/profiles/smartstore_quarter`로 다릅니다. 로그인할 때 해당 스토어를 각각 선택하세요. 같은 네이버 로그인으로 스토어를 전환하는 구조여도 두 프로필에서 각각 올바른 스토어를 선택해야 합니다.

채널 설정의 **로그인 스토어 확인**에 화면에서 현재 선택된 스토어명을 나타내는 요소의 CSS 선택자와 정확한 텍스트를 입력합니다. 기본 예상 이름은 ‘비욘드마이셀프’, ‘쿼터’이며 실제 화면에 표시되는 이름이 더 길다면 그 전체 이름으로 수정하세요. 목록 수집 전과 답변 입력 전에 해당 값이 일치하는지 확인합니다. 일치하지 않거나 선택자가 없으면 수집·전송하지 않습니다.

쿼터 채널의 답변 상호는 ‘쿼터’입니다. 다른 정확한 상호를 사용한다면 **답변에 사용할 상호**에서 수정하세요. 공통 답변 템플릿의 `{{shop}}`에 채널별 상호가 반영됩니다. 빈 상호는 공통 설정인 비욘드마이셀프를 사용합니다.

### 날짜가 있는 문의함

카페24의 `start_date/end_date/period`, 하이버의 `from/to`는 한국 시간의 오늘과 30일 전을 수집할 때마다 계산합니다. 원래 전달된 URL은 설정에 보관되고 실제 접속 주소만 갱신됩니다. 미답변 조건 등 다른 검색값은 유지됩니다. 대시보드의 문의함 링크도 현재 날짜로 열립니다.

연결 설정에서 조회 기간을 1~365일로 바꿀 수 있습니다. **조회 날짜 자동 갱신**을 끄면 직접 입력한 URL의 날짜를 사용합니다. 설정 변경 후 다시 시작해도 선택을 유지합니다.

## 연결 순서

1. **채널 연결 → 연결 설정**에서 미리 등록된 문의 관리 URL을 확인합니다. 처음에는 자동 수집을 끈 채 저장할 수 있습니다.
2. 서버를 종료하고, 화면이 있는 PC에서 `npm run login -- cafe24`처럼 실행합니다. 열린 브라우저에서 직접 로그인·2단계 인증을 마치고 문의 화면을 연 다음 터미널에서 Enter를 누릅니다.
3. `npm start`로 다시 실행합니다. 실제 DOM 구조에 맞게 선택자를 입력합니다. 브라우저 개발자 도구로 확인하거나 개발자에게 매핑을 요청합니다. 비밀번호나 세션 파일을 채팅에 붙여 넣지 마세요.
4. 설정이 끝난 문의함의 **이 문의함 수집**을 선택하고 **자동 수집 활성화**를 켜서 저장합니다. 아직 설정하지 않은 문의함은 수집 선택을 해제해 둘 수 있습니다. **실제 운영 → 지금 수집**으로 수집 결과와 원문을 대조합니다.
5. 문의 ID·본문·고객명이 확인되면 답변을 편집·검토하고 전송합니다. 게시된 답변 원문까지 확인되어야 완료 처리됩니다.

서버 실행 중 10분마다 활성 채널을 수집합니다. 수동 수집 완료 시 다음 주기는 10분 뒤입니다. 종료·절전 중에는 수집하지 않습니다. 로그인 만료·화면 변경은 해당 채널 오류로 표시되며 다른 채널은 계속 처리합니다.

로그인 명령은 채널 설정만 읽으며 문의·초안·전송 상태를 변경하지 않습니다. 첫 실행에서 DB가 없으면 등록된 기본 주소를 사용합니다. 브라우저를 닫아 세션을 저장했다는 메시지만으로 로그인이나 수집 성공이 확인되는 것은 아닙니다.

클라우드에 그래픽 브라우저 화면이 없다면 직접 로그인을 끝낼 수 없습니다. 개인 PC에서 프로그램을 실행하는 방법을 권장합니다. 로그인 세션을 자동 복제하거나 캡차를 우회하지 않습니다.

## 선택자 계약

아래는 **테스트용 화면 예시**이며 실제 쇼핑몰의 선택자가 아닙니다.

```json
{
  "ready": "main.inquiry-list",
  "row": "article.unanswered",
  "idAttribute": "data-id",
  "title": ".title",
  "customer": ".customer",
  "body": ".body",
  "product": ".product",
  "date": "time",
  "link": "a.detail",
  "next": "a.next",
  "empty": ".empty-state",
  "login": "form.login",
  "detailIdentity": "main.inquiry-detail",
  "detailIdAttribute": "data-id",
  "editor": "textarea[name=reply]",
  "submit": "button[type=submit]",
  "confirm": "",
  "postedReply": ".seller-reply"
}
```

| 필드 | 의미 |
| --- | --- |
| `ready` | 로그인 후 표시되는 문의 목록 컨테이너. 로그인 화면과 구별되어야 합니다. |
| `row` | 미답변 문의 한 건의 행. |
| `idAttribute` | 행의 안정적인 고유 ID 속성. 목록 순번·고객명은 사용하지 않습니다. |
| `title`, `customer`, `body`, `product`, `date` | 각 행 안에서 찾는 선택자. `body`는 필수입니다. `date`는 파싱 가능한 날짜에 사용하며 생략하면 수집 시각을 사용합니다. |
| `link` | 행 안의 고유 상세 페이지 링크. 같은 출처의 HTTPS 링크여야 합니다. |
| `next` | 다음 페이지 버튼. 선택 사항. 한도 도달·반복 페이지는 오류 처리합니다. |
| `empty` | 문의가 없다는 명시적 표시. 행이 0개이면 이 요소를 확인해야 정상 빈 목록으로 인정합니다. |
| `login` | 로그인 필요 상태를 탐지하는 요소. 선택 사항. |
| `detailIdentity`, `detailIdAttribute` | 상세 화면의 문의 요소와 ID 속성. 목록 ID와 다르면 전송하지 않습니다. |
| `editor` | 답변 입력 요소. textarea, input, contenteditable을 지원합니다. |
| `submit` | 실제 답변 게시 버튼. |
| `confirm` | 추가 확인 버튼이 필요한 경우 지정합니다. |
| `postedReply` | 해당 문의의 게시된 판매자 답변 본문. 입력란·전체 채팅방이 아닌 실제 결과와 정확한 내용을 비교합니다. |

`row`, `next`, `postedReply`는 표준 CSS 선택자를 사용하세요. 고유 링크 없이 열리는 상세 화면, iframe·Shadow DOM·가상 스크롤·파일 업로드가 필요한 플랫폼은 `src/connectors.js`에 별도 어댑터를 구현해야 할 수 있습니다.

대화형 채널에는 **각 메시지/문의 회차별 고유 ID**가 필요합니다. 중복 키는 `(모드, 채널, 수집함, 문의 ID)`입니다. 변경된 본문으로 기존 문의를 덮어쓰지 않으므로 메시지 단위로 매핑하세요.

## 불명확한 전송 결과

전송 버튼 클릭 이후 연결이 끊기거나 서버가 종료되면 ‘게시 확인 필요’가 됩니다. 자동 재전송하지 않습니다. 플랫폼 원문을 확인한 뒤 **게시된 답변 확인** 또는 **미게시 확인 · 대기로**를 선택하세요. 이미 동일 답변이 있으면 추가 게시 없이 완료 처리하며, 다른 답변이 있으면 중복 게시를 막습니다.

## 상품 실측 수집

**상품 실측 DB → 웹에서 수집**에서 공개 상품 상세 URL(최대 50개)과 선택자를 입력합니다. 상품명은 페이지 전체에서, 사이즈와 수치는 각 행 안에서 읽습니다.

```json
{
  "name": "h1.product-name",
  "row": "table.measurements tbody tr",
  "size": "td:nth-child(1)",
  "length": "td:nth-child(2)",
  "shoulder": "td:nth-child(3)",
  "chest": "td:nth-child(4)",
  "waist": "td:nth-child(5)"
}
```

위 선택자도 예시입니다. 이미지 실측표·범위·인치 단위는 추측하지 않고 오류로 남깁니다. 텍스트의 cm 수치만 읽으며 직접 입력과 JSON 가져오기도 지원합니다. 전체 카탈로그 탐색과 키·몸무게만으로 추천 사이즈를 추정하는 기능은 포함하지 않습니다. 정확한 상품명이 일치하는 실측과 개인차 안내를 초안에 반영합니다.

## 패션플러스 빈 목록과 건수 진단

두 문의함이 모두 비어 있다는 사용자 확인을 바탕으로, 빈 목록일 때 페이지 표시가 생략되는 경우를 처리합니다. 확인된 목록의 헤더·본문이 공유하는 영역 안에서 정해진 `No data`/`자료 없음` 문구를 확인하고 실제 문의 행이 없어야 합니다. 다른 표·사이드바·상태 요약의 0건은 근거로 삼지 않습니다. 긍정적인 전체 건수와 빈 목록 문구가 충돌하면 실패하며 로딩 표시가 보이면 기다립니다. 0건 결과는 네트워크 로딩 종료와 추가 대기 후 재확인합니다. 초기 빈 화면 뒤 실제 조회 응답이 도착하면 그 문의를 읽습니다.

목록 읽기에 실패하면 `diagnostics/fashionplus-{qna|notifications}-pagination.json`을 갱신합니다. 실패 원문이나 문의 배열은 직렬화하지 않으며 화면 구조와 제한된 집계 수치/불리언 값만 저장합니다. 파일 저장 실패는 원래 수집 오류를 가리지 않습니다. 사용자 PC에서 실제 빈 목록 문구는 아직 확인하지 않았으므로 지원하는 표시와 다르면 자동 진단 자료로 추가 확인합니다.
